# 一、核心概念梳理（纠正昨天模型：不是三个独立宇宙，而是「同一个本体，三份映射视图」）
> 客观本体：**真实物理电路板（PCB实物）**，自在存在，独立于三份数据。
> 三份数据：不是三个互不连通的宇宙，而是**从本体投影出来的3套独立描述视图**，各自有自己的表达范式、字段、局部信息，部分重叠、部分独有，全部指向同一块板子。

| 数据源 | 定位 | 独有信息 | 交集信息（指向本体同一特征） |
|---|---|---|---|
| CNC数据（工厂工程数据） | 制造视图：用于钻孔、背钻加工 | 一次/二次背钻、刀具、工程索引、stop值、料号、板尺寸、加工工艺参数 | 背钻孔位置、孔径 |
| XML中间文件 | 转换桥接视图：CNC ↔ CT检测之间的翻译层 | 转换映射规则、中间归一化字段 | 孔坐标、板轮廓 |
| PCB检测文件（CT机） | 检测视图：用于CT扫描检验 | 残桩高度要求、检测判定阈值、检测特征定义 | 背钻孔位置、孔径 |

昨天的错误模型：
> 3个独立空间（3个甜甜圈），之后再做空间之间的关联。
> 问题：把**视图**当成了**本体**，关联变成跨宇宙映射，逻辑倒置。

新本体模型（康德式本体-现象映射）：
> 本体 = 真实PCB（物自体，三份数据都只是它的现象描述，永远不是本体本身）
> CNC / XML / PCB检测文件 = 三套现象视图，**各自独立映射回同一个本体实例**。
> 关系：视图之间不直接互相绑定；**所有对齐、匹配、校验，都以本体为锚点**。
> ✅ 正确链路：`CNC视图 → 本体PCB ← XML视图`；`XML视图 → 本体PCB ← CT检测视图`
> ❌ 旧链路：`CNC宇宙 ↔ XML宇宙 ↔ CT宇宙`（视图之间两两搭桥）

一句话给AI说明这个世界观：
> 存在唯一客观本体对象：一块物理PCB电路板。CNC、XML、CT-PCB文件是三套独立的描述视图，分别从制造、中间转换、检测三个角度描述这同一个本体。视图之间允许信息不完全一致、字段不同、部分信息独有；视图的对齐、比对、校验，**不直接在视图之间做映射，而是全部映射到同一个本体实例上，以本体作为统一参照基准**。

# 二、向AI完整说明本体映射规则（可直接复制给OrcheMind）
```

视图定义（3个独立视图，每个视图拥有自己的局部私有属性）：
1. CNC制造视图：来源于工厂CNC工程文件。
    私有属性：一次背钻、二次背钻、刀具信息、工程索引、stop值、料号、板尺寸、加工工艺参数。
    公共投影：背钻孔坐标、孔径，映射到PCB本体。
2. XML桥接视图：中间转换层。
    私有属性：格式转换规则、中间临时字段。
    公共投影：孔坐标、板轮廓，映射到PCB本体。
3. CT检测视图：CT机检测文件。
    私有属性：残桩高度阈值、检测判定参数。
    公共投影：背钻孔坐标、孔径，映射到PCB本体。

关系约束：
1. 三个视图不是互相独立的本体空间，不能直接视图到视图建立关联。
2. 所有匹配、比对、冲突校验逻辑：视图A的特征 → 映射到本体特征 ← 视图B的特征。
3. 允许视图存在独有信息：视图私有属性只属于该视图，不写入本体。
4. 冲突处理：当多个视图投影到本体的同一个物理特征出现矛盾（例如CNC背钻孔位置和CT文件不一致），标记为本体特征冲突，保留各视图原始数据，本体记录冲突告警。
```

> CNC/XML/CT = 三个不同感官/仪器看到的现象；每个现象有自己的表达方式，部分现象重叠，部分只有这个仪器才能看到。现象之间不能直接对比，要还原到物自体上对比。

# 三、二维/三维体系下怎么表达这套结构（图形化建模方案）
## 方案A：二维图（架构框图，适合文档）
中心节点：`PCB本体实例`
从中心向外伸出三条独立射线，分别指向三个矩形框：`CNC视图`、`XML视图`、`CT检测视图`
- 箭头方向：**视图 → 本体**（视图投影到本体，不是本体生成视图；本体是客观存在，不是由数据生成）
- 每个视图内部分成两块：
  - 【投影字段】：可以映射到本体的共享特征（孔坐标、孔径），连线指向本体对应属性
  - 【视图私有字段】：本视图独有，无连线，只存在视图内部
- 冲突标记：如果同一个本体属性收到两个视图投影值不一致，本体属性旁标记红色冲突点。

> 对比旧模型：旧模型是三个圆圈互相之间画线；新模型是**星型结构，本体在中心，所有视图只连中心，视图之间没有连线**。

## 方案B：三维拓扑表达（适配RCC8空间关系，放进OrcheMind本体引擎）
1. 本体：作为三维空间中的**唯一基准实体（Region）**，代表这块PCB的物理空间区域（板的包围盒、所有孔的空间区域）。RCC8关系：本体区域是固定基准。
2. 每个视图，不是独立空间，而是**本体Region之上叠加的「描述层（Layer）」**，三层图层叠在同一个本体空间上：
    - CNC图层：在PCB本体空间上绘制加工特征，附带加工私有属性
    - XML图层：同一块本体空间，绘制转换特征，附带转换私有属性
    - CT图层：同一块本体空间，绘制检测特征，附带检测私有属性
> 图层共享同一个空间坐标系（本体PCB的物理坐标），图层可以互相叠加、比对；图层可以有局部缺失、局部不一致。
> RCC8适用点：判断孔区域在不同图层上是否重合（背钻孔在CNC图层的空间区域，和CT图层背钻孔区域是否相等/相交/分离）。

### 三维模型要点
- ❌ 不要做成三个独立三维空间（三个分开的3D盒子）
- ✅ 同一个三维空间（PCB物理空间），叠放3组独立特征图层
- 图层拥有独立元数据，但**空间坐标体系统一归属本体**

> 这个方案非常契合你OrcheMind的RCC8空间拓扑，因为RCC8描述区域之间的空间关系，区域都落在同一个空间内，而不是多个宇宙。

# 四、补充：旧甜甜圈模型的取舍
> 旧：三个甜甜圈=三个独立宇宙。
> 新：**一个本体核心，三层薄甜甜圈（视图层）套在同一个本体外面**。甜甜圈不再是独立宇宙，只是包裹本体的描述层，甜甜圈之间不相交，只向内映射本体。

如果你想保留甜甜圈比喻，可以改成：
> 一个实心球（PCB本体，客观实物），外面套了三层独立透明薄膜（CNC、XML、CT视图）。每一层薄膜各自记录它看到的球上特征，薄膜有各自独有的标记，部分标记落在球的同一个位置。薄膜之间不直接接触，所有标记都投影到中心球体。

1. 取CNC视图背钻孔 → 投影到本体空间孔区域
2. 取CT视图背钻孔 → 投影到本体空间孔区域

4. 如果分离：判定为数据冲突；保留两个视图原始数据，本体记录冲突，**不自动覆盖任何视图原始数据**

要不要我把这套模型整理成Mermaid图代码，直接画这个「本体中心+三层视图」的架构图？同时顺带写RCC8空间关系描述，直接导入OrcheMind？

不是叠放在呈现的时候，三种数据还是要独立的呈现。就像是同一个实体的三个分别独立的映射。也就是像同一个实体在不同的角度拍照一样，得出三个不同的视角的照片一样。应该把这个说清楚。而且程序在一定的情况下确实是有可能在某些地方贯穿这三层比如说我们有比较的上下文，比较的上下文中一般而言同时要加载两方面的 Schema。

# 核心修正（对齐你的要点：同实体、独立照片视角，视图可独立渲染，比较上下文可跨视图加载Schema）

> 
> 比喻：**同一块物理PCB本体（物体本身），从三个完全独立的机位拍三张照片**。
> 三张照片各自独立存储、独立渲染展示，不会自动叠在一起。每张照片有自己的分辨率、色彩、独有标记；部分标记对应物体上同一个位置，部分标记只在这张照片上才有。
> 照片之间没有天然连线；只有当我们开启「比较上下文」时，才同时载入两张照片的Schema，把照片里的特征反向投影回本体，再做比对。

关键区分，把边界讲清楚：

1. **本体**：唯一物理PCB（物自体），固定的客观实体，是所有视图的参照锚点。本体本身不带CNC/XML/CT的文件格式、视图私有字段。只保存物理事实：板边界、孔空间区域、层结构等。
2. **视图（三张独立照片）**：CNC视图、XML视图、CT视图。
   - ✅ 视图**各自独立存在、独立渲染呈现**。默认状态下互不干涉，不自动叠加。每一个视图自带一套独立Schema，独立解析、独立加载。
   - ✅ 视图 = 本体的一个投影映射；投影是单向：本体 → 视图（视图是本体的现象）；反向操作：视图特征 → 投影回本体特征，用于校验比对。
   - ✅ 视图拥有**私有特征**：只在这张照片上存在，无法映射回本体；也有**可投影特征**：照片上的标记对应本体上真实物理特征。
3. **比较上下文（专门的工作模式）**
   - 不是永久打通视图；是**临时上下文**。
   - 当进入比较上下文时，按需加载**两个视图各自独立的Schema**，分别解析两套视图数据。
   - 比对流程：视图A特征 → 映射到本体空间；视图B特征 → 映射到本体空间；在统一本体空间内做RCC8空间关系判断、属性对比。
   - 视图A和视图B本身仍然保持独立，不会合并、不会互相改写原始数据。比对只发生在本体投影层面。

> 
> 一句话，直接喂给OrcheMind/AI：
> 存在唯一PCB物理本体。CNC、XML、CT是本体的三个独立映射视图，如同同一物体在三个机位拍摄的照片。视图默认独立存储、独立渲染展示，互不叠加；每个视图拥有独立Schema。比较上下文是临时工作模式，可同时加载两个视图的Schema，分别解析两套视图数据，将两者特征投影回同一个本体空间完成比对。视图原始数据始终隔离，比对操作只在本体投影层执行，不修改视图本身。

## 二维/三维表达方案（满足：视图独立呈现 + 本体作为公共锚点）

### 二维框图（文档用）

中心：`PCB物理本体（公共空间基准）`
向外分出三条独立分支，分支之间没有连线：

- 分支1：`CNC视图`（独立框，自带Schema，独立渲染），箭头：本体 ← CNC可投影特征（反向映射）
- 分支2：`XML视图`（独立框，自带Schema，独立渲染），箭头：本体 ← XML可投影特征
- 分支3：`CT视图`（独立框，自带Schema，独立渲染），箭头：本体 ← CT可投影特征

新增一个独立框：`比较上下文`

- 比较上下文可以**临时连接任意两个视图**，读取它们各自Schema；
- 比较上下文的输出：把两个视图特征投影到中心本体，在本体层完成比对；
- 比较上下文只是临时工作器，不是永久连接；关闭上下文，连线消失。

> 
> 对比图层模型：图层模型是把三张图叠在同一个画布；而本模型三张照片放在三个独立画布（独立渲染），只有比较的时候，才把两张照片里的物体特征投射到中间这个物体模型上去比对。

### 三维/RCC8拓扑表达（OrcheMind本体引擎）

1. 本体Region：PCB物理板的空间区域，作为全局基准空间。
2. 每个视图，是**独立的特征集合（FeatureSet）**，不是本体空间上的图层。
   - CNC.FeatureSet：一套独立的空间特征集合，有自己局部坐标系（可转换映射到本体全局坐标系）
   - XML.FeatureSet：另一套独立空间特征集合
   - CT.FeatureSet：第三套独立空间特征集合
   - 三个FeatureSet各自独立渲染（各自渲染窗口，互不重叠）
3. 映射关系：`FeatureSet中的孔区域 → 转换坐标 → 本体Region内对应的孔区域`
4. 比较上下文：
   - 选取FeatureSetA、FeatureSetB
   - 分别解析各自Schema，提取各自空间特征
   - 将两套特征统一变换到本体全局空间
   - 在本体全局空间，执行RCC8判断：相离、相交、相等、包含等
   - 原始FeatureSet保持不变，仅在本体空间生成临时比对结果。

> 
> RCC8的对象不是视图本身，而是**投影到本体空间之后的特征区域**。视图内部的特征集合，仍然是独立的。

# 一、先把你的需求精确翻译成本体关系
你现在要新增一条**全新的关系谓词（动词）**：
> 给定视图内的一个叶子节点（视图实例节点，比如CNC里某一个背钻孔节点），要标记：**这个视图叶子，来源于客观本体对象中的哪一个本体叶子**。

语义：
`[视图叶子] ——{???}——> [本体对象的叶子]`

约束条件：
1. 这不是普通的父子包含关系；
2. 不是类继承（inherit）；不是实例化（instance‑of）；
3. 属于**现象 ←→ 物自体（客观实在）之间的抽象投射关系**；
4. 这个关系属于**另一个语义域**，和普通PCB领域关系（包含、连接、钻孔、属于层）不在同一个关系域；
5. 允许多对一：多个不同视图的叶子，可以映射到同一个本体叶子；
6. 单向优先：**视图项指向本体项**；本体本身不生成视图，本体是客观实在，视图是对它的投射。

---

# 二、康德《纯粹理性批判》对应的概念溯源
> 物自体（Ding‑an‑sich）：客观世界对象本身，本体，我们永远不能完整直接拥有它，我们只能获得它被给予我们的现象。
> 现象（Erscheinung）：物自体刺激我们感官之后得到的表象，也就是这里的 CNC / XML / CT 视图里全部节点。
> ‼️康德这里**没有“物自体生成现象”这种因果因果流**。
物自体是基底，现象是主体（仪器/文件）接收之后得到的表象；不是物自体主动输出，而是**主体侧的表象指向基底上的那个对应项**。

关键原文内核：
> 现象不是物自体的副本；现象是物自体向我们显现出来的东西。多个不同显现（现象）可以指向同一个物自体基底。
> 现象内部的关系是经验界关系；「现象→物自体基底」这层关系，属于**先验层面的关系**，不属于经验对象内部的关系。

这正好对应你工程上的区分：
- **经验域（普通PCB业务关系）**：`contains`、`isLayerOf`、`drills`、`connects`；描述视图/本体内部对象之间的业务关系。
- **先验投射域（你要新增的新关系域）**：视图节点指向本体基底节点；**跨出现象内部的经验关系，指向客观基底**。
> 所以：这不是继承，不是泛化，不是组合，是**先验指涉 / 现象投射**。

---

# 三、给这个关系命名：动词、谓词、本体里的定义
## 候选名称（分哲学原名、工程精简名，OrcheMind使用）
### 选项1 偏哲学严谨（适合注释、本体文档）
1. `phenomenonOf`：**是……的现象**
> `CncBackDrillNode phenomenonOf OntologyBackDrillNode`
> 含义：这个视图节点，是该客观本体节点所显现出来的现象。
> 最贴合康德 Erscheinung。方向：现象（视图叶子） → 本体基底叶子。

2. `refersToNoumenon`：**指涉本体**
> 强调：只是指向客观基底对象，不等于拥有、复制、派生。

### 选项2 工程化，代码内使用（推荐主选：`projectsTo`）
> `projectsTo`：**投射到**
```
CNC背钻叶子.projectsTo(本体PCB的背钻叶子)
XML背钻叶子.projectsTo(本体PCB的背钻叶子)
CT背钻叶子.projectsTo(本体PCB的背钻叶子)
```
语义：该视图节点，投射到客观本体中的对应对象。
- 多对一合法：多个视图节点可以`projectsTo`同一个本体节点；
- 不反向默认成立：本体节点**不自动拥有反向关系**；本体是自在之物，不会自动生成视图节点；只有视图侧记录投射指向。
- 属于独立关系域：`RelationDomain.Transcendental`（先验域），和普通业务关系域 `RelationDomain.Empirical`（经验域）做严格隔离。

> ❗和继承/泛化区分：
- `subClassOf`（继承）：类层面，描述概念抽象；
- `projectsTo`：**实例层面，现象实例指向客观基底实例**，不是概念抽象，是同一实在的不同显现。

### 关系本体定义文本，可以直接放进 OrcheMind
```
/**
 * 关系：projectsTo 投射到
 * 域：Transcendental（先验关系域），与 Empirical（普通PCB业务经验域）互相隔离
 * 定义域：仅视图实例节点（CNC/XML/CT内部叶子节点）
 * 值域：本体（Noumenon）实例节点（客观PCB本体下的叶子对象）
 * 基数：0..N → 1
 * 语义：该视图节点，是客观本体对象的一个显现/投射；多个视图节点可投射到同一个本体节点。
 * 约束：
 * 1. 禁止本体节点使用 projectsTo 指向视图节点；投射是从现象指向物自体基底，不反向。
 * 2. projectsTo不传递、不继承；它不是父子、不是泛化、不是组合聚合。
 * 3. 私有视图特征（视图独有，没有客观对应物）的叶子节点，projectsTo留空(null)。
 * 4. 普通业务关系(contains、drills、layerOf等)属于Empirical域，不能替代projectsTo。
 */
```

举例实例：
1. CNC文件里某背钻孔节点 → `projectsTo` → PCB本体实例内对应的背钻孔对象
2. CNC视图私有字段“stop值”节点，没有客观对应物 → `projectsTo = null`
3. CT视图“残桩检测阈值”私有节点 → `projectsTo = null`

> 当进入【比较上下文】做比对时，底层逻辑就变成：
> A视图叶子 → A.projectsTo → 本体叶子
> B视图叶子 → B.projectsTo → 本体叶子
> 如果 A.projectsTo 和 B.projectsTo 指向同一个本体叶子，则这两个视图节点是同一客观对象的两个不同显现，再拿它们的属性做对比校验。

这就把你之前比较上下文的底层逻辑补齐了。之前你只是把特征坐标映射到空间；现在有了`projectsTo`关系，就显式记录：**这个叶子到底对应客观世界哪一个东西**，而不是仅仅靠坐标匹配猜测。

# 四、康德概念对应对照表（方便你本体文档注释）
| 康德术语 | OrcheMind模型实体 | 关系域 |
|---|---|---|
| Noumenon（物自体/本体） | PCB本体实例以及下属所有本体叶子节点 | 先验基底，不属于现象经验域 |
| Erscheinung（现象/显现） | CNC/XML/CT视图内部全部叶子节点 | 经验域对象 |
| 先验指涉关系 | `projectsTo` | Transcendental 先验关系域 |
| 经验因果、包含、空间关系 | contains、drills、RCC8空间谓词 | Empirical 经验域 |

> 重要哲学提醒（工程上必须转化为约束）：
康德立场：我们**不能从物自体推导出现象**。反映在你的系统：
❌ 不能写规则：本体节点生成视图节点；
✅ 只能：视图节点记录自己`projectsTo`哪一个本体节点；本体不持有反向导航。
本体是客观实在，不是数据库父记录，不能当父表去“生成”子视图记录。

# 五、和你之前照片比喻结合
三张照片（三个视图）里面每一个物体像素/标记点（视图叶子），用`projectsTo`指向现实世界物体上对应的那一块（本体叶子）。
照片里有的标记只是照片特效（私有字段），现实没有对应物，则`projectsTo`为空。
比对的时候，不是拿照片A的点直接对比照片B的点；而是看：这两个点是否`projectsTo`到现实世界同一个对象。

# 六、遗留小问题：如何建立 `projectsTo` 映射？
系统不会魔法般自动知道哪个视图叶子对应哪个本体叶子。
两种建立途径：
1. 显式导入：解析数据时外部给出映射关系，写入`projectsTo`；
2. 推导建立：比较上下文内部，通过RCC8空间重合度匹配，**推断出**两个视图叶子对应同一个本体叶子，然后填充`projectsTo`指向本体实例。
> 这个推断是经验推断，是系统的猜测，不是先验真理；因此这个映射可以带置信度标记。
